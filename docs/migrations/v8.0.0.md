# Migrating to 8.0.0

This guide covers the breaking changes in 8.0.0 and what you need to do about them.
For the full list of every change, see [`CHANGELOG.md`](../../CHANGELOG.md).

All packages are versioned in lockstep, so this major bump applies to every
`Supabase.*` package at once.

## 1. Parameterless `Table.Delete(...)` now returns the deleted rows

`IPostgrestTable.Delete(QueryOptions?, CancellationToken)` (and its `Table`
implementation) now returns `Task<ModeledResponse<TModel>>` instead of `Task`.

**Why:** a delete that is blocked by a row-level-security policy, or that matches no
rows, is not an error in PostgREST — the request succeeds and returns an empty
representation. The old signature discarded the response body, so callers could not
tell "nothing was deleted" apart from "deleted" and saw a phantom success
([#334](https://github.com/supabase-community/supabase-csharp/issues/334)). The rows
were already on the wire (`QueryOptions.Returning` defaults to `Representation`); the
method now hands them back. The SDK still does not throw on an empty delete — you
decide how to react.

**What you need to do:**

- If you already `await` the call and ignore the result, no source change is needed —
  but you must recompile against 8.0.0.
- If you assigned the result to a `Task`, or captured the method group as a `Func<Task>`
  / delegate, update the type to `Task<ModeledResponse<TModel>>`.
- To act on whether anything was actually deleted, inspect `Models`:

```csharp
// Before (8.0.0 removes this shape — the deleted rows were unavailable)
await client.Table<Todo>()
    .Filter("id", Operator.Equals, "1")
    .Delete();

// After — the deleted rows come back in Models
var response = await client.Table<Todo>()
    .Filter("id", Operator.Equals, "1")
    .Delete();

if (response.Models.Count == 0)
{
    // Nothing was deleted: the row did not exist, or an RLS policy hid it.
    // Decide how to react.
}
```

The `Delete(TModel model, ...)` overload is unchanged — it already returned
`Task<ModeledResponse<TModel>>`.

## 2. Newtonsoft.Json replaced with System.Text.Json

The SDK now uses `System.Text.Json` instead of `Newtonsoft.Json` for all serialization.

**Why:** `System.Text.Json` is built into the .NET runtime, reducing external
dependencies and enabling trimming / ahead-of-time (AOT) compilation — important
for cloud-native workloads. Performance is also significantly better.

**What this means for you:**

If you use the SDK to query models and only interact with types like
`Client.Table<T>()`, `Auth`, `Realtime`, and `Storage`, **no changes are needed** —
the SDK handles serialization internally, and the wire format is unchanged.

If you have custom code that does any of the following, read the sections below:

- Define your own model classes with JSON attributes
- Call `JsonConvert.Serialize/Deserialize` directly
- Pass custom serialization options or converters to the SDK

### Custom models with JSON attributes

If your project defines model classes with `[JsonProperty]` from Newtonsoft.Json:

```csharp
// Before (Newtonsoft.Json) — no longer works
using Newtonsoft.Json;

[JsonObject(MemberSerialization = MemberSerialization.OptIn)]
public class MyModel
{
    [JsonProperty("user_id")]
    public int UserId { get; set; }
}

// After (System.Text.Json) — update to this
using System.Text.Json.Serialization;

public class MyModel
{
    [JsonPropertyName("user_id")]
    public int UserId { get; set; }
}
```

Key changes:

- Replace `using Newtonsoft.Json;` with `using System.Text.Json.Serialization;`
- Replace `[JsonProperty("name")]` with `[JsonPropertyName("name")]`
- Remove `[JsonObject(...)]` declarations; System.Text.Json opt-in is less common
- If you were using `[JsonIgnore]`, it still exists — no change needed
- For `NullValueHandling`, use `[JsonIgnore(Condition = JsonIgnoreCondition.WhenWritingNull)]` instead

### Direct serialization calls

If you serialize or deserialize JSON manually in your own code:

```csharp
// Before (Newtonsoft.Json) — no longer works
using Newtonsoft.Json;
var json = JsonConvert.SerializeObject(obj);
var obj = JsonConvert.DeserializeObject<MyModel>(json);

// After (System.Text.Json) — update to this
using System.Text.Json;
var json = JsonSerializer.Serialize(obj);
var obj = JsonSerializer.Deserialize<MyModel>(json);
```

For most cases, `JsonSerializer` is drop-in compatible. If you were relying on
Newtonsoft-specific behavior (like lenient string-to-number coercion), you may
need to create a `JsonSerializerOptions` with `NumberHandling = JsonNumberHandling.AllowReadingFromString`.

### Serialization options passed to the SDK

If you were creating or modifying `JsonSerializerSettings` before passing them
to the SDK, update to `JsonSerializerOptions` from `System.Text.Json.Serialization`:

```csharp
// Before (Newtonsoft.Json)
var settings = new JsonSerializerSettings { NullValueHandling = NullValueHandling.Ignore };

// After (System.Text.Json)
var options = new JsonSerializerOptions { DefaultIgnoreCondition = JsonIgnoreCondition.WhenWritingNull };
```

The SDK's public option types (e.g., `ClientOptions`, `PostgrestOptions`) remain
unchanged in shape — they still take serialization options where applicable, just
with the new STJ types under the hood.

## 3. Packages retarget to .NET Standard 2.1

Every shipped package now targets `netstandard2.1` (previously `netstandard2.0`).

**Why:** `netstandard2.1` unlocks newer runtime APIs and lets the SDK drop
compatibility shims.

**What you need to do:**

- If your project runs on **.NET Core 3.0+, .NET 5+, .NET 8/10, or a recent
  MAUI / Mono 6.4+ / Xamarin target**, you already satisfy `netstandard2.1` — no
  change is needed.
- If you target **.NET Framework** (any version — `netstandard2.0` is its ceiling)
  or a **pre-`netstandard2.1` runtime** (Mono < 6.4, older Xamarin/Unity), you can no
  longer reference these packages. Move to a `netstandard2.1`-capable target, for
  example by migrating the consuming project from .NET Framework to .NET 8+.
